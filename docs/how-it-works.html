The friction02 / 17

The last mile of a release is where the two days go

What "the last mile" actually is

  • App name, subtitle, a 100-char keyword field with rules
  • Screenshots in exactly the right pixel sizes
  • Prices in 175 territories, availability, age-rating questionnaire
  • Review contact + notes, in-app purchase readiness
  • Then a dozen traps that only appear after you press Submit

Why I know

14 apps on the App Store. The week before this hackathon I did this by hand for a new one: two days, a 55-char limit I'd forgotten, a rerun that silently skipped a localization, and a default that would have left an in-app purchase buyable in one country.

I keep a 64-row error index of every trap I've hit. That index is the product.

Say it like this"This isn't a hypothetical. I lived it last week and I wrote every trap down. The agent is that list, running by itself."
The rule03 / 17

Nothing types. Ever.

The Taskmaster track asks for an agent that watches for a trigger, decides what to do, and acts across apps end-to-end. Most entries open with someone typing into a chat box. Ours opens with a build upload.

What wakes the agent

App Store Connect has real webhooks (push, not polling). When a build finishes processing, Apple sends a signed POST to our Cloud Run URL. That POST is the start button.

What the human does

Upload a build, the way they already do. Once per app, seed a fact sheet (what the app does, who it's for, brand colours). That's it.

What comes back

Days later, Apple's review verdict arrives by the same webhook. Approved → job closed. Rejected → the agent routes the rejection to the right stage and re-runs itself.

Say it like this"The only human action in the whole demo is uploading a build — which I'd do anyway. The trigger is Apple telling us the build is ready."

One document per job: which stage is done, what was written, what Apple said. A crash or a retry resumes at the first unfinished stage.

The trigger, up close05 / 17

How a webhook becomes a job

step 1

Verify it really is Apple

Apple signs every POST with a shared secret: header x-apple-signature: hmacsha256=…. We recompute the HMAC over the raw body and compare in constant time. Wrong signature → 401, nothing happens.

step 2

Resolve the build

The payload names a buildUploads id. Observed: the build shares that UUID. Fallback: newest VALID build on an allowlisted app. Net: Cloud Scheduler reconciles every 30 min in case a delivery is missed.

step 3

Allowlist, then job

Only app 6803901837 may be written to — 13 other apps are live and earning. Passes → Firestore job document → Pub/Sub message with the job id → worker picks it up.

19:35:55 xcodebuild: Upload succeeded 19:37:25 webhook buildUploadStateUpdated {'oldState': 'PROCESSING', 'newState': 'COMPLETE'} 19:43:56 buildUpload 2143692d… cfBundleVersion=2 state=COMPLETE → job-2-d7d5d7 created → published to shipwright.jobs

Agents 2 + 3 · critique loop07 / 17

Give the critic tools, not taste

Writer

Drafts the metadata

Reads the fact sheet and the last critique. Follows the three-name doctrine: the store name is a keyword-led ranking asset ("SnipStash: Clipboard Manager"), subtitle is a second search field, keywords fill what's left.

→draft←rejection list
Critic

Tries to reject it

First calls a deterministic validator (a tool): 30/30/100 char limits, fill ≥27/27/97, zero words repeated across fields, no plurals, no "app", no brand names, no hardcoded price. Then applies judgment: claims the facts don't support, slogan-y subtitles. Approves by calling exit_loop.

Why a separate agent

A writer asked to check its own work says "looks good". A second agent whose only job is to reject, with a validator it must call, catches a 31-character name every time.

ADK pattern

LoopAgent(sub_agents=[writer, critic], max_iterations=4). Output flows through session state (output_key). On every real run so far it converged in one round.

Result on SnipStash

name 28/30 · subtitle 27/30 · keywords 97/100 · zero cross-field repeats · review notes are numbered test steps.

Say it like this"Two models: one writes, one is paid to say no. The 'no' agent has Apple's rules as a tool, so the model spends its judgment on the things code can't see."
Agent 4 · screenshots08 / 17

Real pixels. An image model never touches the UI.

Why

From the error index: let an image model "redraw" a screenshot and it hallucinates numbers and text — a "SAVE 30%" badge you don't have. App Review reads every word on a screenshot.

How

Five real simulator captures at 1320×2868. Gemini writes a headline + sub-line per panel that echoes the metadata keywords. Code (Pillow) paints a brand-gradient backdrop, the caption, and pastes the capture pixel-exact with rounded corners and a shadow.

Sizes (a trap in itself)

Apple's API slot for 6.9" phones is named APP_IPHONE_67 and takes 1320×2868; APP_IPHONE_69 does not exist. The web uploader wants 1284×2778 instead. We render both.

Panel order is a rule too: panel 1 establishes the category (a searcher must instantly recognise what this is), 2–3 the mechanic, last one trust/privacy.

Say it like this"The screenshots are real device captures on a branded background with keyword captions. No generated UI — that's how you get rejected for a number that isn't in the app."

Operator items (web-only by design)

Some gates have no API: App Privacy must be published, the 2026 medical-device banner, the Paid Apps Agreement, the first IAP attaching via the web draft. The agent doesn't pretend — it lists them as one-click items on the job page.

The one I didn't plan for11 / 17

Two rejections no API field could ever show

Preflight also hands the real captures plus the fact sheet to Gemini with one question: which on-screen claims can this build not back?

[WARN] panel 5: 'Multi-device sync … across iPhone, iPad, and Mac' — iCloud sync and the Mac app are explicitly not in v1.0 [WARN] panel 5: 'Custom keyboard: Insert snippets in any app' — not in v1.0 [WARN] panel 1: 'Password: Sunshine!42' — cleartext password visible in sample data [WARN] panel 1: 'pwd=nT5rQxK9' — meeting password inside a Zoom link

Why it matters

Guideline 2.3.1 / 3.1: metadata and screenshots must match the binary. A paywall promising sync the app doesn't have is a rejection. So is a password on screen one.

Why only vision finds it

There is no field for "your paywall over-promises". The only way to catch it is to look at the pixels with the fact sheet in hand — exactly what a reviewer does.

Say it like this"This is my favourite part. Gemini looked at the actual screenshots and caught a paywall promising features the build doesn't have — and a password in the sample data. A reviewer would have bounced both."
Agent 6 · submission + safety rails12 / 17

Semi-irreversible, so it sits behind three gates

DRY_RUN=falseANDALLOW_SUBMIT=trueANDapp ∈ ALLOWED_APP_IDS→submitted:true

Dry-run by default

Every write returns the exact payload it would have sent; the job page shows it. I watched it plan a full release before letting it perform one.

Hard allowlist

Checked on webhook ingress and before every single write. A bad write to a live app record is damage, not a bug.

Credential security

The .p8 lives in Secret Manager only. .gitignore blocks it; the Dockerfile never copies it; the service account reads it at runtime and mints a 15-minute ES256 JWT.

The submit call itself: POST reviewSubmissions → POST reviewSubmissionItems → PATCH submitted:true, then read the version state back. Uploaded ≠ attached ≠ submitted ≠ approved ≠ live — five different states.

Say it like this"Submitting costs your place in the review queue if you're wrong, so it's behind two flags and an allowlist. And the Apple key exists in exactly one place: Secret Manager."
